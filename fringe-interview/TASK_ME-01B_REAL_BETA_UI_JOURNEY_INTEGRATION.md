# TASK ME-01B — Real Beta UI Journey Integration

## 1. Entry point UI/app individuato

The repository had no real tester-facing application entry point consuming BI-01. The historical HTML shell was a demo/setup renderer: its “start simulation” action only marked the simulation step as visited and then allowed navigation to a pre-generated report file.

ME-01B introduces the minimum executable entry point:

`scripts/run_private_beta_ui_server.js`
→ `src/app/privateBetaUiServer.js`
→ `src/app/privateBetaUiJourneyEntryPoint.js`
→ `runIntegratedPrivateBetaJourney`

The local server uses Node's built-in `http` module; no UI framework or external server framework was added.

The browser entry is:

`GET /private-beta`

and journey submission is:

`POST /private-beta/journey`.

## 2. Flow storico precedente

The previous tester-visible artifacts were generated by `scripts/test_generate_interactive_shell_html.js` using:

- `renderInteractiveInterviewShellHtml`;
- `buildInteractiveSessionPayload`;
- pre-existing session output under `tmp/` when available;
- a static report HTML file.

The shell's `fakeStartButton` did not invoke the Interview Runtime or BI-01. It only set `simulationVisited = true`, persisted local browser state and switched panels. The report navigation targeted a separate generated HTML file.

This legacy/demo flow remains in the repository because broad renderer cleanup is explicitly out of scope.

## 3. Punto di integrazione BI-01

`runPrivateBetaUiJourneyEntryPoint` is the only new application bridge. It maps tester UI fields into the already-authorized BI-01 arguments and calls `runIntegratedPrivateBetaJourney` directly.

It does not implement a second onboarding, consent, interview or feedback state machine. BI-01 remains responsible for:

- Beta Session creation/lifecycle;
- M1-04 onboarding;
- M1-05 consent enforcement;
- authorized material access;
- Interview Runtime/session runner;
- M1-03 safe application errors;
- Professional Perception report availability;
- M1-06 feedback;
- M1-07 operational logging;
- session closure.

The UI bridge keeps material values behind getters so BI-01 remains the authority that decides when CV/JD/answers are actually accessed.

## 5. Journey realmente raggiungibile

From the new canonical entry page a tester can provide:

1. onboarding choices;
2. consent accept/refuse;
3. target role, CV and JD only when consent is accepted in the UI;
4. text interview answers;
5. optional feedback submit/skip.

The POST enters BI-01, which runs the canonical sequence:

`Beta Session → Onboarding → Consent → Material Acquisition → Interview Preparation → Interview Runtime → Professional Perception Report → Feedback → Session Closure`

with safe M1-03 errors and M1-07 events.

The new entry point therefore removes the previous manual separation between setup shell, runtime/session generation and static report navigation at the application-entry level.

The UI remains intentionally minimal. It does not implement ME-02/ME-03/ME-04 report/Representation UX.
